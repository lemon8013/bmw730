## 架构结论：不拆微服务（2026-10-07 问答）
- 用户问"是否需要拆分成微服务"，结论：**不需要**，维持模块化单体。
- 依据（实测）：后端 413 个 py 文件 / 4.9 万行 / 106 张表 / 9 个业务模块；模块间耦合集中在
  shared(612) + core(195)，业务模块互相只引用共享内核，不互相引用。
- 强事务耦合点（拆分即破）：admin 成长体系写操作必须委托 platform 的
  `GrowthService.apply_event` / `PointService.adjust`（幂等+行锁+version+等级重算+审计）；
  ops 依赖 admin 的 `sys_audit_log` 模型与 system 的 `SysJob`。这三处一旦变成 HTTP 就
  要 Saga/补偿，收益为零。
- 4 个前端（5173/5174/5175/5176）已各自独立部署，"按产品分离"这条已经做完了，
  后端没有独立发布的组织压力。
- 唯一该独立成进程的是**采集 Agent / 指标采集器**（要跑在被监控主机上），那是独立程序，
  不是把后端拆成微服务。

## 收尾 GL-09 / GL-12 + CentOS 部署（2026-10-07 晚）
- **内置调度器落地** `app/ops/scheduler/`（GL-09 关闭）：
  - `lock.py`：`job_lock()` 用 `pg_try_advisory_lock`（会话级、非阻塞），非 PG dialect 直接 yield True，
    所以 sqlite/单测不会炸。多副本只有赢家执行。
  - `jobs.py`：`rollup_metrics` / `evaluate_alerts` / `run_availability_probes` / `purge_expired_data`，
    每个 job 自带 session 事务；`run_guarded()` 吞掉异常（一次 tick 失败不能杀掉调度器）。
    `lock_id()` 用 **crc32 不用 hash()**（str hash 每进程随机，会让锁失效）。
  - `runtime.py`：`OpsScheduler`（APScheduler AsyncIOScheduler）。purge 用 CronTrigger 固定
    `OPS_SCHEDULER_PURGE_HOUR`（interval 会随容器重启漂移，把清理拖到业务时段）。
  - main.py lifespan 启停；默认 `OPS_SCHEDULER_ENABLED=false`，compose/env 显式打开。
  - **坑（第二次遇到，勿忘）**：`date_trunc` 同时出现在 SELECT 和 GROUP BY 会渲染成两个不同绑定
    参数，PG 报 "column must appear in the GROUP BY"。解法恒定：**子查询里先算桶，外层 group by 别名**。
    `app/ops/metrics/repository.py` 的 `_AGGREGATE_RAW_SQL` / `_AGGREGATE_HOURLY_SQL` 就是这么写的。
  - rollup upsert 用 `pg_insert().on_conflict_do_update(index_elements=[metric_key,dimension_key,bucket_at])`，
    重跑是重算而非重复行。
- **自监控落地**（GL-12 大部分关闭）：`app/ops/availability/probe.py`
  HTTP/TCP/DNS/SSL 四种执行器（httpx + socket + ssl，**没引新依赖**）；
  `AvailabilityService.run_due_checks()` 按 interval_seconds 过滤；
  `seed_ops_self_monitoring()` 按 `check_code=vctn_api_self_health` 幂等播种（不改运维已改过的行）。
